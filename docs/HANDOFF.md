## Phase 0 plan, as originally written (completed — see "Phase 0 result" below)

Half a day, on a branch in `pyExamScan_v2`, before any merge work. Everything downstream depends on the outcome.

Rewrite `scan_functions.py` against `opencv-python-headless`, using `cvtColor`, `medianBlur`, `threshold`, `erode`, `dilate`, `connectedComponentsWithStats`, `getAffineTransform`, and `warpAffine`. Remove scipy and scikit-image from `pyproject.toml`, and delete the two `collect_submodules` sweeps from `pyexamscan.spec`.

Brandon previously dropped OpenCV to chase better PyInstaller behavior, but that was the plain `opencv-python` package. Use the **headless** variant, which omits the GUI bindings that pull in Qt and the video libraries.

Verify by running an already-graded exam PDF through old and new code and diffing the bubble dictionaries and the graded CSV. They should match exactly. Then build with PyInstaller on macOS and Windows, and install the macOS build on a machine that has never had Python.

Two failure modes. Alignment that looks plausible but is slightly off means the affine inverse-map direction is backwards; skimage's `warp` treats its transform as an output-to-input map, so `cv2.warpAffine` needs `flags=cv2.WARP_INVERSE_MAP`. An error on the size-15 median blur means grayscale conversion is happening after the blur rather than before, since `cv2.medianBlur` only accepts kernels above 5 on 8-bit input.

**If it passes, proceed to phase 1 and abandon the Tauri plan. If PyInstaller is still unreliable with a clean dependency tree, stop and reopen the question.**

## Phase 0 result (2026-09-04)

Done on branch `phase0-opencv-rewrite` (committed — see "Update" below for the commit hash and push). Touches exactly four files: `scan_functions.py`, `pyproject.toml`, `pyexamscan.spec`, `uv.lock`.

The rewrite matches the original exactly. `results.csv`, `resultsperquestions.csv`, `resultsforCanvas.csv`, and `exam_key.csv` came out byte-identical between the old (scipy/scikit-image) and new (opencv) code, run against `tests/scannedSheets.pdf` through the full `Scanner` pipeline, not just the isolated functions. The aligned JPEGs are not bit-identical — up to 11/255 per-pixel difference, from JPEG re-encoding and cv2's bilinear sampling differing slightly from skimage's — but that magnitude never crosses a threshold decision, which is why the final dictionaries and CSVs match exactly regardless. Neither of the two predicted failure modes showed up: alignment was correct on the first attempt (the `WARP_INVERSE_MAP` direction reasoning in this doc held), and the size-15 median blur ran fine (grayscale-before-blur ordering was preserved). `cv2.threshold` ended up unused; it applies `<=` at the threshold value where the original code and every other spot in this rewrite use strict `<`, so the comparison stayed a plain numpy expression instead, to keep the match exact rather than approximate.

PyInstaller built cleanly on macOS (Apple Silicon, arm64), and the resulting `.app` launches standalone — run directly by path outside the dev venv, no dev tools on `PATH` beyond what's already on this machine — and stays up with no stderr output, which is the strongest local proxy available for "never had Python." It has **not** been installed on a genuinely clean machine; that check is still open.

**The bundle got bigger, not smaller — this contradicts `scanner-packaging-options.md`'s prediction.** Old (scipy + scikit-image, with the `collect_submodules` sweeps): 222 MB. New (opencv-python-headless): 253 MB. The audit's "one 40 MB wheel replaces about 150 MB" estimate was the wheel download size, not what PyInstaller collects. `cv2` alone accounts for 118 MB unpacked: a 40 MB `cv2.abi3.so` plus a full video-codec stack this project never touches — `libavcodec`, `libx265`, `libaom`, `libSvtAv1Enc`, `librav1e`, `libavformat`, even `libtesseract`. "Headless" strips the GUI/window bindings, not the codecs; there's no way to select OpenCV submodules from the prebuilt wheel. Trimming this (a source build with only `imgproc`, or Option B's hand-rolled numpy from the same audit doc) is a real option later if the size matters, but it wasn't attempted here — flagging it for a decision rather than deciding it. Per the plan's own risk section, a bundle this size is "invisible to a user who downloads it once a year," so this did not block the phase 0 gate, which was about correctness and PyInstaller reliability, not size.

**A separate, pre-existing bug turned up while checking the artifacts, unrelated to this rewrite.** The Windows job's upload step (`.github/workflows/build.yml:63`) only grabs `dist\PyExamScan\PyExamScan.exe`. The spec builds in PyInstaller's onedir mode (`EXE(..., exclude_binaries=True)` + `COLLECT(...)`), so that `.exe` is a launcher stub that needs the rest of `dist\PyExamScan\` — its DLLs, `.pyd` extension modules, and data files — sitting next to it to run at all. The macOS side doesn't have this problem: `BUNDLE` wraps `COLLECT`'s full output into the `.app`, and the DMG step packages that whole `.app`, so the 113 MB compressed macOS artifact is complete (matches the 253 MB uncompressed `.app` measured locally, a normal compression ratio for a mix of already-compressed binaries and compressible data).

**Fixed.** `build.yml` now zips `dist\PyExamScan\` with `Compress-Archive` before uploading, the same shape as the macOS DMG step, and the release job's file list points at the zip instead of the loose `.exe`. This ended up being two small coordinated edits rather than the one line it looked like at first — the release job's file reference had to move too, or it would have pointed at a path that no longer existed inside the artifact. ## Two real bugs found, one fixed

**Points were silently lost round-tripping a key CSV — fixed above.** `pyExamPaper/key_generator.py` writes ten columns ending in `points`. `pyExamScan_v2/openQ.py:save_key_csv` wrote nine and had no `points` column, though its reader did parse one. Building an exam with per-pool point values, opening the key in the scanner's open-question editor, and saving lost every per-question point value with no error. This was the strongest argument for the merge, and is what phase 1's `keyformat.py` exists to fix.

**MD questions are worth too much — not yet fixed, scoped to phase 3.5.** `key_generator.py` writes the full point value onto every dropdown row, and `gradeResults` sums per column, so a three-dropdown MD tagged `(1 pt)` scores three points. The plan is to fix it with the same points-distribution rule phase 3.5 introduces for OR and MT — but as of phase 3, this bug is still live and has been deliberately carried forward unfixed into `exam_key_writer.py` (see phase 2's result below), specifically so each phase's verification stayed a pure code-move check rather than mixing in a behavior change. `tests/test_build_tab_logic.py` and `tests/test_build_migration.py` both assert the bug reproduces exactly, as a tripwire for phase 3.5 to update once it actually lands the fix. **The MD points bug is fixed, not just documented.** `exam_key_writer.py` gained `_distribute_points(total, n)`, a largest-remainder split to two decimals (1.0 point over 3 slots → `[0.34, 0.33, 0.33]`, matching the spec's own worked example) used for MD, OR, and MT alike. `tests/test_build_migration.py`'s tripwire (`test_md_question_points_bug_preserved`, added in phase 2 specifically to flag this moment) is renamed `test_md_question_points_bug_fixed` and now asserts `[0.5, 0.5]` for that fixture's 1-point, 2-dropdown MD question. If any exam built between phase 1 and now had a multi-dropdown MD question, its printed key overweighted that question — worth checking recent gradebooks, per the original bug note.

**Parsing splits guard checks between two files, deliberately.** Four of the spec's five rejection rules (OR with >6 or <2 items; MT with no lefts; MT referencing a right label that doesn't exist) are structural and need no randomness, so they live in `parser.py`'s new `_parse_or`/`_parse_mt`, each returning `(question, warning)` instead of the other parsers' plain `question` — the warning text names both the file and the block number, matching (and slightly extending) the existing "Block N: ..." style. The fifth rule — an MT whose right-side count still exceeds six *after* distractor trimming — can only be known post-trim, and trimming is random sampling, which `parser.py` deliberately never does (that's `exam_builder.py`'s job, matching how oversized MC/MA answer lists were already handled by `_trim_mc_answers`). So `exam_builder.py` gained a parallel `_trim_mt_rights` plus a small `_trim_and_filter` wrapper that runs both trims and drops anything that still doesn't fit, identifying the rejected question by file name and stem text since no block number survives that far. This split isn't called out explicitly in the spec; flagging it here in case a future read of the spec makes it sound like all five guards should be in one place.

**OR's unconditional shuffle is real and was the trickiest part.** The spec is explicit that OR items must scramble for display regardless of `shuffle_answers` — the source file lists them in true-answer order, so leaving them alone would print the answer key as the question. `exam_builder._finalize_or_mt` does this unconditionally for every OR question, every version, independent of both build-time shuffle flags. One judgment call the spec doesn't fully settle: MT's *right-side* shuffle is gated on `shuffle_answers` (same as every other answer-choice list — MC, MA, MD), while MT's *left-side* order (which becomes the exam's own numbered question slots, "Question 8", "Question 9"...) is gated on `shuffle_questions` instead, per the spec's literal wording for that half. Worth a second look if MT's on-paper randomization ever looks off.

**Verification.** 75 tests pass (`uv run python -m unittest discover tests`): the pre-existing 42 (with `test_build_migration.py`'s golden fixtures regenerated from this repo's own new code rather than pyExamPaper's, since pyExamPaper never supported OR/MT either — there's no independent implementation left to diff the new content against, so correctness there rests on manual inspection of the regenerated HTML/MD/key plus the dedicated suite) and 33 new ones in `tests/test_or_mt.py`, covering: both source formats parsing correctly, including a right label shared by two lefts and non-sequential right-label declaration order (mirroring real pool content surveyed in the spec); all five guard rejections; `_distribute_points`'s arithmetic; an OR at exactly the six-item ceiling; and a full build→render→key round trip whose OR assertions are derived from the built object's own (randomly shuffled) state rather than a hardcoded letter, so the test doesn't depend on a particular random seed. ## Review pass (2026-09-05)

A full read of the merged branch against all three plan documents, looking for errors, security problems, and workflow blocks. Four things were found and fixed; the sections above are left as the dated record of what was true when they were written, so where this section contradicts one of them, this section wins.

**An ordering question numbered anything other than 1..N crashed exam generation.** `parser._parse_or` checked the item count but never the rank sequence, and `exam_key_writer.build_key_data` then looks up every rank from 1 to N to map it to a display letter. A bank numbered from zero, missing a number, or repeating one raised `KeyError` — caught by `build_tab`'s blanket `except`, so the user got a raw traceback after the HTML and Markdown were already on disk and before the key was written. `_parse_or` now rejects it as a fifth structural guard, in the same "Block N in file.txt" style as the other four, naming the numbering it actually found.

**`scanner.py`'s own `exam_key.csv` export dropped `point_values`.** The line right after it prints "Load this file in Key File next time to skip re-scanning the key sheet," and `gradeResults` reads points per column, so taking that advice silently regraded every question at the flat bubble value. This is the same loss `merge-and-package-plan.md` opens with, surviving in a writer phase 1 didn't audit — `keyformat.py` was the only writer, as claimed, but one caller wasn't handing it the field. `self._key_data['point_values']` was already loaded in `__init__`; it's now passed through.

**Matching questions printed their own answer key when "shuffle answers" was off.** Phase 3.5 gated MT's right-side scramble on `shuffle_answers` — flagged above as a judgment call the spec didn't fully settle. It was the wrong call. With the ordinary authoring pattern, `[r1]left1` / `[r2]left2` / `[r3]left3`, the key came out A, B, C on every build, which is the exact failure the spec's OR reasoning describes ("an unscrambled OR has the answer A, B, C, which is not a question"). `_finalize_or_mt` now scrambles MT rights unconditionally, alongside OR items; MT's lefts still follow `shuffle_questions`, since they are the exam's own question slots rather than a choice list. ## Facts worth not rediscovering
